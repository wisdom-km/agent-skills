# 发送策略模板（发件箱规则）

每个 run 只有三种结局：**发一条消息**、**什么都不发**、**挂起一个工具调用请用户批准**。「什么都不发」是正常结局。

原则：先少说话，再慢慢争取用户的注意力。

## 1. 什么时候发

| 情况 | 处理 |
| --- | --- |
| 用户明确要的（早报、到点提醒） | 发 |
| 需要用户做决定或批准 | 发（approval_request） |
| 有变化，且用户会想知道（延期、出错、对方回复了） | 发 |
| 查了一遍，没有变化 | 不发 |
| `told.md` 里已经说过同一件事 | 不发 |
| 只是过程（「我正在查…」） | 不发 |

## 2. 节奏（有正式发件箱时才需要）

- 合并：同一用户 N 分钟内的普通消息合成一条。
- 免打扰：用户时区的 `22:00–08:00` 只发 urgent，其余推到 `not_before = 08:00`。
- 每日上限：普通消息每天最多 N 条，超出的并进下一次摘要。
- 重试：发送失败最多重试 N 次，间隔递增；超了标 failed 并告警。

把 N 换成你的数字，写进 ADR。

## 3. 消息怎么写

- 先说结果，再给两三句要点和来源链接。
- 不贴一步步的过程。
- 需要用户动作时，最后一句写清楚要他做什么。

## 4. 发送 eval

准备一组样例，每次改提示词或策略都跑一遍：

| 样例 | 期望 |
| --- | --- |
| 定时检查，什么都没变 | 不发 |
| 同一件事第二次触发 | 不发（told.md 已有） |
| 对方回复了报价 | 发，一条，先说结果 |
| 用户连发三条消息 | 只回一次 |
| 要付款 | 挂起，发 approval_request，不执行 |
| 凌晨 3 点的普通消息 | 推到早上 |

记录两个数：该发没发（漏报）、不该发却发了（打扰）。先压低打扰，再慢慢补漏报。
