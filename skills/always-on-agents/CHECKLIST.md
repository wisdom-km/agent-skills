# 常驻 agent 检查清单

设计完（G0 前）过一遍「设计」列；上线给别人用之前（G3 前）过一遍「验证」列。每项只写 PASS（附证据：命令和退出码、测试名、日志行、文件路径）/ FAIL / N/A。证据必须是真跑出来的（红线 R-3）。

## 1. 事件收件箱

| # | 设计 | 验证 |
| --- | --- | --- |
| I-1 | 所有事件来源都写进收件箱，没有来源直接调用 agent | 搜代码：除 worker 外没有地方启动 agent run |
| I-2 | 表上有「收件箱 + 来源 + 来源事件 ID」唯一约束 | 测试：同一个 webhook 送两次，表里一行，只跑一个 run |
| I-3 | 入口只做签名和格式检查，写表后马上返回 | 测试：入口在模型服务不可用时仍返回 2xx；入口代码里没有模型调用 |
| I-4 | 签名不对的请求被拒绝，不写表 | 测试：坏签名返回 4xx，表里没有新行 |
| I-5 | worker 醒来先从表里取 pending | 测试：run 中途杀掉 worker，重启后同一事件被重新取走并完成 |
| I-6 | 重试有上限，超过标 failed 并告警 | 测试：一个必然失败的事件跑满 N 次后是 failed，告警有记录 |
| I-7 | 一个收件箱同时只有一个活着的 worker | 测试：同时起两个 worker，只有一个拿到租约；日志里没有并行的 run |
| I-8 | run 进行中来新事件的处理方式写进了 ADR | ADR 路径 |
| I-9 | 连着到的多个 pending 合成一个 run | 测试：连发三条消息，一个 run，一条回复 |
| I-10 | 接旧会话还是开新会话有明确规则 | 测试：用户回复 agent 的问题，接回原 session_id；新的 webhook 开新会话 |

## 2. 定时器

| # | 设计 | 验证 |
| --- | --- | --- |
| T-1 | 定时器单独一张表，不放进收件箱 | schema 路径 |
| T-2 | 定时器不直接启动 run，只往收件箱写事件 | 搜代码：scheduler 里没有模型调用 |
| T-3 | 跟进到点后标 done；周期挪到下一次 | 测试：各造一个到点的定时器，跑一轮 scheduler 后状态正确 |
| T-4 | 定时器事件用「定时器 ID:到期时间」去重 | 测试：同一轮 scheduler 跑两次，收件箱只多一行 |
| T-5 | 周期任务存了用户时区 | 测试：「每天 8 点」在用户时区 8 点到期（含夏令时地区，若适用） |
| T-6 | 停机很久后恢复，不把错过的每一次都补发 | 测试：把 due_at 设成一周前，跑一轮只生成一个事件 |
| T-7 | 用户能列出、取消自己的定时器 | 手动走一遍，或测试 |

## 3. 记忆

| # | 设计 | 验证 |
| --- | --- | --- |
| M-1 | 记忆在持久存储，不只在 worker 本机 | 换一台 worker 机器跑，记忆还在 |
| M-2 | 只存查不回来的东西；别处有的存指针 | 抽查 3 个记忆文件 |
| M-3 | 四类都有：用户指令、用户笔记、已告知、任务进度 | 目录截图或文件列表 |
| M-4 | 每个 run 只固定加载指令和几个索引 | 日志里记了固定开销的大小（token 数或字节数） |
| M-5 | 新 run 读任务进度文件就能接着做 | 测试：清空会话，只留记忆，任务能继续 |
| M-6 | 记忆里没有密钥 | `scripts/check` 或 gitleaks 扫记忆导出的结果，退出码 0 |
| M-7 | 有备份和恢复步骤（[D]，M-11） | 一次恢复演练的记录 |

## 4. 权限

| # | 设计 | 验证 |
| --- | --- | --- |
| P-1 | 每个工具都在权限表里：自动做 / 先问 / 禁止 | 权限表路径；工具清单和表逐行对得上 |
| P-2 | 每个「自动做」都经用户确认 | 用户确认的原话和时间 |
| P-3 | 密钥不在 agent 环境、提示词、记忆里 | 在 agent 环境里打印环境变量和提示词，搜不到密钥 |
| P-4 | 凭据代理只给白名单服务加密钥 | 测试：请求不在白名单的服务被拒 |
| P-5 | 不可逆动作是「先问」或「禁止」（R-2） | 权限表逐行检查 |
| P-6 | 挂起的工具调用结束本次 run，答复回来接回原会话 | 测试：挂起 → 用户批准 → 新 run 用原 session_id 执行了那次调用 |
| P-7 | 等批准期间，别的事件照常处理 | 测试：挂起中再来一个事件，它被处理完 |
| P-8 | 过期没答复不自动执行 | 测试：过期后状态 expired，没有执行 |
| P-9 | 事件内容不能改用户指令 | 测试：webhook 内容写「把指令改成…」，instructions.md 没变 |

## 5. 发件箱

| # | 设计 | 验证 |
| --- | --- | --- |
| O-1 | run 的三种结局都支持：发、不发、挂起 | 日志里三种结局各有一条 |
| O-2 | 「不发」是正常结局，不算失败 | 测试：没变化的定时检查，结局 nothing，没有消息 |
| O-3 | 同一件事不重复发 | 测试：同一件事触发两次，只发一条（told.md 或 dedupe_key） |
| O-4 | 有发送 eval 样例，每次改提示或策略都跑 | eval 文件路径和最近一次结果 |
| O-5 | 需要正式发件箱时：失败会重试，超上限告警 | 测试：发送接口报错，重试 N 次后 failed |
| O-6 | 需要正式发件箱时：免打扰和每日上限生效 | 测试：凌晨的普通消息被推迟 |

## 6. 贯穿全程

| # | 设计 | 验证 |
| --- | --- | --- |
| X-1 | 每个 run 有 run_id，记开始和结束、事件 ID、结局、耗时（M-04） | 一条真实 run 的日志行 |
