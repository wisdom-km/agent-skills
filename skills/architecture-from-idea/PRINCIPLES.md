# 原则：先讲成能听懂，再给正式定义

向用户解释术语时用本文件。每个词先给日常说法，再给机制和出处。不要用本文件替代架构决定。

## 复杂度

- 日常：房间里线缠成一团。你要换一盏灯，却得先搬沙发、剪掉别的线，还不知道哪根线是灯的。这就是复杂。
- 正式：让系统难理解、难修改的结构因素。它是「某个人在某个时候做某件事」时的体验，按花在该部分的时间加权。三个症状：改动放大、认知负担、未知的未知（最糟）。两个根因：依赖、晦涩。目标之一是「显而易见」。《APOSD》第 2 章。

## 耦合与内聚

- 日常：耦合是积木粘死了，拆一块带起三块。内聚是一个抽屉只放一种东西。
- 正式：耦合是模块间依赖的强度；内聚是一个模块职责是否围着同一个设计决定。可改性战术：增加内聚（拆模块、重新分配职责）、降低耦合（封装、中介、抽象公共服务、限制依赖）。SAP §8.2。《Pragmatic Programmer》Tip 17 正交性。

## 抽象、接口、实现

- 日常：插座是接口，冰箱、台灯是实现。你只会用插座，不必拆开冰箱。
- 正式：模块 = 接口 + 实现。接口有形式部分（签名）和非形式部分（行为、调用顺序等）。《APOSD》第 4 章。好的接口让常见用法最简单，并且「有点通用」：功能反映当前需要，接口不绑死当前需要（第 6 章）。

## 深模块与浅模块

- 日常：深模块像自动门：你只推一下，里面有很多机关。浅模块像每颗螺丝都要你自己拧。
- 正式：深模块功能强、接口简单（Unix 五个 I/O 系统调用是典型）。浅模块是红旗。「类越多越好」是误区（classitis）。《APOSD》第 4 章。

## 信息隐藏与泄漏

- 日常：厨房把门关上，外面的人不必知道灶怎么点火。如果每个房间都要按同一种奇怪开关才能用电，这个决定就泄漏了。
- 正式：每个模块封装几个设计决定（Parnas）。`private` 不等于信息隐藏：一串 getter/setter 仍会泄漏。信息泄漏 = 一个设计决定反映在多个模块。按执行顺序切模块（时间分解）是红旗。《APOSD》第 5 章。

## 依赖规则与依赖倒置

- 日常：家的规矩由屋里的人定，不能由快递公司定。快递可以按屋里规定的门口交货，屋里不引用快递公司的内部表格。
- 正式：源码依赖只能指向内圈；内圈不能提外圈声明的任何名字，也不能用外圈数据格式。跨边界用依赖倒置：内圈定义接口（端口），外圈实现它，于是源码依赖与控制流可以方向相反。[Uncle Bob, 2012](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html)。

## 端口、适配器、接缝

- 日常：端口是插座规格。适配器是插头。换电器不拆墙。只做了一个插头，还不算真的能换；做了两个（真的和假的），接缝才算成立。
- 正式：业务核心通过端口（接口）与外部世界交谈；适配器把端口接到数据库、网络、UI、测试假实现。一个适配器是假想接缝，两个适配器才是真接缝。

## 装配根

- 日常：所有插头在电箱里接好，房间里不再临时接线。
- 正式：只有一个地方构造具体实现并注入。入口文件只装配，不写业务分支。

## 可插拔与延迟绑定

- 日常：灯座事先留好，以后换灯不拆天花板。越晚决定用哪盏灯越好，但灯座本身得划算。
- 正式：把预计会变的东西藏在稳定接口后面，在编译期、部署期或运行期再绑定（参数化、插件、多态）。SAP §8.2、§8.4。

## 质量属性场景

- 日常：不说「要快」，而说「晚上 8 点，100 人同时打开首页，第 95 个人也要在 2 秒内看到内容」。
- 正式：六要素：刺激源、刺激、环境、制品、响应、响应度量。可测、无歧义。再用效用树按业务价值 × 技术风险排序。SAP §3.3、§19.4。

## 技术债、曳光弹、原型

- 日常：战术式像赶作业抄近路，以后要加倍还。原型是草稿纸，用完扔掉。曳光弹是先打一发真子弹看弹道，这支枪留下继续用。
- 正式：技术债会复利。《APOSD》第 3 章。原型为学习，必须标明一次性；曳光弹是端到端骨架，留下再长大。《Pragmatic Programmer》Topic 12/13。

## Harness、上下文工程、两类约束

- 日常：Harness 是给助手准备的工作台：地图、工具、检查清单。上下文是助手桌上的位置，桌面有限，只放高信号的纸。有的规矩写在便条上（助手自己决定听不听），有的装成门锁（每次都会拦住）。
- 正式：人负责设计环境和反馈环，agent 执行（[Harness Engineering](https://openai.com/index/harness-engineering/)）。上下文是有限的注意力预算，目标是最小的高信号 token 集合（[Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)）。非确定性指令（提示、AGENTS.md、skill）由模型决定；确定性指令（hook、deny、CI、lint）由环境每次执行。[Claude Code 最佳实践](https://code.claude.com/docs/en/best-practices)。不断强调仍被忽略的规则，应升级为 hook 或检查。

## 红旗速查（《APOSD》）

改动放大；认知负担；未知的未知；浅模块；时间分解；信息泄漏；透传方法和透传参数；把复杂度推给调用者；模块级全局状态；`utils` / `helpers` 垃圾桶；入口文件又装配又写业务。
