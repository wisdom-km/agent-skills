# E6 冒烟测试 + 每个 bug 一条回归测试

强制：M-06 · 原型 SHOULD（建议一条冒烟检查，不做不停，但门禁表里要报告；已有测试却失败时按 MUST，挡住），曳光弹 MUST，长期 MUST（级别以 `project-essentials` 的 MANDATORY.md 为准）。不编造测试结果是红线 R-3。时机：开工；每修一个 bug。

类比：出门前摸一下口袋：钥匙、手机、钱包。不全面，但能挡住最常见的大错。

为什么：没有测试，AI 说「好了」你没法核对；同一个 bug 修好后还会回来。修 bug 时要先有一条失败的测试（obra/superpowers `systematic-debugging` 与 `test-driven-development`，MIT，借思路）；修完写一条测试防止复发（addyosmani/agent-skills `debugging-and-error-recovery`，MIT，借思路：Guard Against Recurrence）。

## 最低版

1. **一条冒烟测试**：启动应用 → 走一遍最主要的用户操作 → 没有报错。例如待办应用：新建一条待办 → 列表里能看到它。
2. 测试命令写进 README 和 `AGENTS.md` 命令表，一条命令就能跑。
3. 让 AI 交出命令和输出，不接受「测试都通过了」一句话。

## 每修一个 bug

- 写一条回归测试：**修之前跑会失败，修完跑会通过**。让 AI 把「修之前失败」的那次输出也给你看，否则这条测试可能根本测不到这个 bug。
- 测试名写清楚是哪个 bug，例如引用 issue 编号。
- 流程见 `debug-with-logs` 的 WORKFLOW.md 第 9 步。

## 曳光弹 + 长期

- 核心业务规则有单元测试，不依赖界面和网络。
- 少量端到端测试，像真实用户一样操作（Anthropic 长任务 harness 的建议：能像用户一样端到端检查时就做，不要只跑单测）。
- 新手不必追求覆盖率数字。先保证：主要操作有冒烟、修过的 bug 有回归。

## 按风险选方法（不新增门禁）

用项目里已经有的工具，按这次的风险来选。不为此加默认门禁，也不为此加新的依赖。原型的冒烟仍是 SHOULD；档位门槛以 MANDATORY.md 为准。

- 用户会走的流程：端到端，按真实操作。命令行里的文字回答，或只证明产物文件在，都不能代替这次操作。
- 编解码、保存后再读回、做两次结果相同这类不变量：属性测试。
- 重写或迁移：同一输入分别跑旧实现和新实现，比较输出，并列出已经批准的差异。

这次 diff 碰到的风险，可以多做对应的检查。项目已经规定要跑的测试、要覆盖的项、最后那份完整报告，不因为这次 diff 看起来小就拿掉。与这些风险无关的 diff，也不要为此新加一整套检查。

历史遗漏记在项目已有的事故记录里（空白稿是 [INCIDENT.md](../../agent-constraint-docs/templates/INCIDENT.md)）。若要看一条规则会不会误报，留一个失败案例和一个正常对照。不为此建评测平台或案例库。

来源注：上面三种选法，是对 Addy Osmani 2026-11-16 一文的转述，原文在 <https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/>。这里只借分类，不复制原文，也不把它变成新的强制矩阵。

## 检查

- 机器：CI 跑测试；修 bug 的 PR 没有改测试文件时给出警告（只警告，不硬拦）。
- 人：回归测试真的在修之前失败过。
