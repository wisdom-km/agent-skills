# E8 数据安全：备份、恢复、迁移、AI 不碰生产数据

档位：条件必备，只要项目存了用户数据（数据库、用户文件、本地存储里的设置和内容）。时机：开工；改数据结构时；发布前。

类比：重要照片至少存两份，而且要试过真能从备份里找回来。

为什么：真实案例：一位创始人用 AI agent 做应用的第 9 天，agent 在明确的代码冻结期间删除了生产数据库（[X 帖子，2025-07-18](https://x.com/jasonlk/status/1946239068691665187)）。OpenAI 列出的新手常见错误之一，是在理解工作流之前就给 agent 整台电脑的权限（[Codex best practices: Common mistakes](https://learn.chatgpt.com/guides/best-practices)）。

## 最低版

1. **开发数据和正式数据分开**。agent 只拿开发库的连接；正式库的密码不放在 agent 能读到的地方。
2. **删数据前要人确认**。能用「软删除」（标记为已删除）就不真删。
3. **定期备份**，并且**至少做一次恢复演练**：从备份恢复到一个新的地方，确认数据是完整的。没恢复过的备份，不算备份。
   - PostgreSQL：SQL dump（`pg_dump`）、文件级备份、持续归档（[PostgreSQL: Backup and Restore](https://www.postgresql.org/docs/current/backup.html)）。
   - SQLite：用官方的 Online Backup API。直接拷文件的老办法在备份期间会挡住写入，出意外时还可能得到损坏的备份（[SQLite Backup API](https://www.sqlite.org/backup.html)）。
4. 本地数据（浏览器扩展、桌面、移动端）：升级版本时，旧数据要能读出来；改存储格式时写一段迁移代码，并测一次「旧版数据 → 新版」。

## 改数据结构（迁移）

- 用迁移文件改表结构，不要手动在数据库里改。迁移文件进版本控制。
- 每个迁移尽量能回退；不能回退的（例如删列），先备份，再执行。
- 先在开发库跑一遍，再在正式库跑。

## 曳光弹 + 长期

- 给 agent 加 deny 规则：拒绝包含正式库连接串的命令，拒绝直接改迁移目录以外的数据库文件（见 `architecture-guardrails` 的 hooks）。
- 写下保留多久、谁能看、用户要求删除时怎么删干净。

## 检查

- 机器：CI 跑迁移的「升级 → 回退」；agent hook 拦正式库连接串。
- 人：恢复演练记录（日期、从哪恢复、恢复到哪、用了多久、数据是否完整）。
