# RULES

适用对象：仓库里的人和 coding agent。冲突优先级：用户当场的明确指示 > 本文 > ARCHITECTURE > PRD > 历史草案。

## 1. 编码与测试约定

- 错误处理：
- 禁止的逃逸：
- 测试命名：`<结果> when <条件>`，并引用 AC 编号。
- 测试只断言行为，不靠读取源码文本断言。
- 运行日志：按下表；字段、级别和事件表见 ARCHITECTURE §10。

| ID | 规则 | 怎么拦 |
| --- | --- | --- |
| L-01 | 错误要记录：带事件名、request_id、哪个操作、原因。同一个错误只记一次，不在每层重复记 | |
| L-02 | 不吞错：不写空 catch。捕获后要么处理掉并记 WARN，要么带上下文往上抛 | |
| L-03 | core 只用注入的 logger。不 import 具体日志库，不用裸 print / console.log | |
| L-04 | 新加的边界（入口、适配器、外部调用）按 ARCH §10 加日志，并更新事件表 | |
| L-05 | 日志用结构化字段，不用字符串拼接。不记密钥、token、session 值、个人敏感数据。外部输入去掉换行符 | |

## 2. 依赖引入

新依赖要写：用途、许可证、体积、替代方案。许可证白名单：。黑名单：。

## 3. 分支、PR、并行

一次一个切片或一件事。开工前声明要改的切片与热点文件。契约（接口类型）先行合入，再并行实现。

## 4. 测试纪律

同一提交的全量检查只跑一次。失败只重跑失败项。flaky 隔离并开 issue。skip 视为失败。

## 5. 评审清单

- 每个文件只承接一种变化
- 无新增模块级可变状态
- 新依赖边在矩阵之内
- 有命令与退出码作为证据
- 新边界有日志；错误带 request_id 和原因；没有空 catch

## 6. Agent 绝不能做的事

| ID | 禁止 | 怎么拦 |
| --- | --- | --- |
| N-01 | 把密钥写入仓库或日志（日志里同样不记 token、session 值、个人敏感数据） | |
| N-02 | 绕过门禁或扩大已确认范围 | |
| N-03 | 编造测试结果或上游能力 | |
| N-04 | force push / 直推受保护分支 | |

「怎么拦」列只能引用已存在的门禁，否则写 review。

## 7. 文档

一个事实一处。改规格与代码同一 PR。未核实写「未核实」，未测数字写「待定标」。

## 8. 关键架构约束

- 原文（不得删改或弱化）：_例如「UI 不得 import core 内部实现，只能经 seam 调用。」_
- 执行细则：
- 交接时必须原样引用的一句话：
- 完成说明：改了哪些 UI 文件；core 是否未改；seam 是否够用；core 测试命令与结果。

## 9. Definition of Done

只指向已有条文，不另写一套。

| 条件 | 怎样算达到 | 指向 |
| --- | --- | --- |
| 验收标准有证据 | AC 对应检查已跑，留下命令与退出码 | PRD §验收、本文 §4 |
| 未违反禁止清单 | 自审表已填碰到的项 | 本文 §6、ARCH 禁止事项 |
| 出问题能定位 | 新边界有日志；故意触发一次错误，能按 request_id 找到对应日志 | 本文 §1 L-xx、ARCH §10 |
